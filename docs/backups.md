# Backups

Everything that matters exists in **three places**: the live system, a local copy on the NAS
or PBS, and an **off-site** copy in **Backblaze B2**. The off-site part is code:

| Piece | Where | Tool |
|---|---|---|
| B2 buckets (private, SSE-B2 encrypted, **Object Lock**, lifecycle rules); per bucket a **backup key** and a separate **maintenance key**, none able to delete for good, written into Infisical | `tofu/backblaze` | OpenTofu, `Backblaze/b2` provider 0.14.1 |
| Retention (forget/prune, old base backups) with the maintenance keys only; monthly **restore self-checks**; alerts to one webhook | `k8s/apps/backups/maintenance.yaml` (generated), the NAS `restic-maint` container, `k8s/infrastructure/configs/alerts.yaml` | restic 0.20.0, barman-cloud, Alertmanager |
| What goes where, retention, schedules | `ansible/group_vars/all/backups.yml` | the single source for all of the below |
| Postgres (every CNPG cluster): WAL + base backups | `k8s/apps/<app>/database.yaml` (ObjectStore `b2`) | CNPG **Barman Cloud plugin** v0.16.0 |
| App volumes and NAS folders | `k8s/apps/backups/volsync.yaml` (generated by `make render`) | **VolSync 0.17.0**, restic mover |
| Proxmox guests (PBS) | Ansible role `pbs_offsite` (`make pbs-offsite`) | PBS **S3 datastore** + local sync job |
| NAS media library + the operator's personal shares (read-only) | Ansible role `nas_backup` (`make nas-backup`): Backrest in Docker **on the NAS** (default `backup_nas_media: restic-on-nas`) | **Backrest v1.14.1** (restic) → dedicated bucket ([below](#nas-media-and-personal-files)) |

Why these tools: [decisions](decisions.md#off-site-backups-backblaze-b2).
**Total or partial loss** (machines, the NAS, Infisical, the workstation, or everything including
Headquarters): the [disaster-recovery runbook](disaster-recovery.md), printed with `make dr-pdf` into
the emergency kit. It restores in this order: your NAS files (restic from `artzima-nas`), the lab,
app data (Postgres from `artzima-pg`, volumes from `artzima-restic`), then verification. The pause
switches `backup_volsync_paused` and `nas_backup_paused` keep a rebuilt, still-empty system from
backing up over the last good snapshots, and also suspend retention.

## Immutability: what a leaked or rogue key can do

Three layers keep a compromised lab (or a buggy job) from destroying the off-site copies:

1. **No automated key can delete for good.** Every key `tofu/backblaze` makes has `listBuckets,
   listAllBucketNames, readBuckets, listFiles, readFiles, writeFiles`, never `deleteFiles` (which
   is what permanently removes a file *version*). A delete through the S3 API with such a key only
   **hides** the file (a new "hidden" version); the data stays until the lifecycle rule purges
   hidden files after `b2_days_hidden_to_deleted` days. `tofu test` fails if any key gets
   `deleteFiles`, `writeKeys` or bucket-write capabilities.
2. **Object Lock (governance mode)** on the pg, restic and nas buckets (`b2_object_lock_days`, 30):
   every uploaded version is immutable for 30 days, even for the lifecycle rule and for keys with
   `deleteFiles` (only a key with `bypassGovernance`, which nothing here has, could override it).
   B2 can only enable it **when a bucket is created**. restic, barman-cloud and Backrest work
   unchanged: their deletes are "hides", which Object Lock allows. **PBS: off** (`pbs: 0`) until a
   PBS S3 datastore on a locked bucket is verified (its garbage collection deletes chunks and is
   untested against locked versions).
3. **Backup jobs only add; retention runs separately.** The jobs that write backups use the
   **backup** key and never forget/prune: VolSync has no `retain` (prune practically off), the
   CNPG ObjectStores have no `retentionPolicy`, Backrest keeps all snapshots with pruning
   disabled. Retention runs on a schedule with the **maintenance** key:

   | What | Job | Schedule (`backups.yml`) | Key |
   |---|---|---|---|
   | VolSync repos | CronJob `backup/restic-maintenance`: `restic forget --keep-* --prune` per repo | `backup_restic_maint_cron` (Sun 09:00 UTC) | `/k8s/backup/RESTIC_B2_MAINT_*` (Secret `backup/restic-maint`) |
   | Postgres | CronJob `<ns>/<cluster>-retention`: `barman-cloud-backup-delete --retention-policy "RECOVERY WINDOW OF 30 DAYS"` | `backup_pg_maint_cron` (Sun 09:30 UTC) | `/k8s/backup/PG_B2_MAINT_*` (Secret `b2-pg-maint`) |
   | NAS repo | container `backrest-maint` on the NAS (crond): `restic forget --keep-* --prune` | `nas_backup_prune_cron` (Sat 06:00 UTC) | `/ansible/NAS_B2_MAINT_*` |
   | PBS | PBS's own prune + GC inside PBS (one key) | PBS jobs | `/ansible/PBS_B2_*` |

   The pause switches (`backup_volsync_paused`, `nas_backup_paused`) suspend retention as well.

**restic with Object Lock:** nothing to configure. restic (0.17+) never overwrites files; prune
"deletes" packs, which on B2 becomes a hide, and the locked versions stay recoverable for the lock
period. A repo can be rolled back by restoring hidden versions (B2 web UI *Browse Files → Show
hidden*, or `b2 ls --versions`); `restic check` afterwards. Storage cost: hidden files are billed
until the lifecycle rule and the lock allow their purge (lock days + hidden days at most).

## Self-checks (monthly, automatic)

Labelled `artzima.io/self-check`, each prints `RESULT: PASS …` or `RESULT: FAIL …` and exits
non-zero on FAIL (alert `RestoreTestFailed`; `make verify` shows the last result):

- **`backup/restic-restore-test`** (1st of the month, 07:00 UTC): picks ONE VolSync repository
  (month N → repo N, so all get their turn), runs `restic check --read-data-subset=5%`, then a full
  `restic restore latest --verify` into a scratch `emptyDir` and counts the files. Snapshots larger
  than `self_check_restic_max_gib` (20) get the check only.
- **`<ns>/<cluster>-restore-test`** (2nd of the month, 07:00, 08:00, … UTC): creates a scratch
  CNPG cluster that **recovers from the B2 backups** (no WAL archiving, StorageClass
  `nfs-artnas-scratch`, deleted afterwards with its folder under `k8s/_scratch/`), waits until it
  is Ready, counts the tables, deletes it. Its RBAC may delete/exec only that scratch cluster.
- Run one now: `kubectl -n backup create job --from=cronjob/restic-restore-test rt-manual`, then
  `kubectl -n backup logs -f job/rt-manual`.

## Alerts

ONE endpoint: Infisical `/k8s/alerts/WEBHOOK_URL`. Empty = the alerts exist (Alertmanager UI,
Grafana, `make verify`) but are not sent. Alertmanager posts its standard webhook JSON.

Since 2026-11-24 the endpoint is **Headquarters** (HQ), the operator's command center: it turns each
alert into one notification (repeats held back for 4 h; warning and critical push to the phone, info
doesn't; resolved alerts send a short note). HQ is on the tailnet only, so:

- `k8s/apps/monitoring/hq-egress.yaml`: an ExternalName Service the Tailscale operator turns into a
  proxy to HQ's tailnet name (`${hq_tailnet_fqdn}` <- Infisical `/k8s/settings/HQ_TAILNET_FQDN`).
- `WEBHOOK_URL` = `http://hq-egress.monitoring.svc.cluster.local:4800/hooks/lab/<token>`. The token is
  HQ's (`~/.hq-secrets/lab-alerts.json` on the HQ machine); without it HQ answers 401.
- After a rebuild of the lab: nothing to do (both values are in Infisical). After HQ moves to
  another machine or gets a new token: update `HQ_TAILNET_FQDN` and/or `WEBHOOK_URL`, then
  force-sync the ExternalSecrets (`alert-webhook` in monitoring, `cluster-secret-vars` in flux-system).
- Flux health reaches HQ through Alertmanager (`FluxResourceNotReady`), so Flux has no own Provider.
- Info-level alerts go nowhere (route `severity =~ "info|none"` -> null), on purpose.
- **Not wired yet:** Backrest and `restic-maint` on the NAS. They post from the NAS, which is not on the
  tailnet and cannot use the cluster's egress, so they don't reach HQ. Their failures still show as
  missed-backup alerts in Alertmanager where a metric exists.

| Alert | Fires when |
|---|---|
| `VolSyncBackupMissed`, `PostgresBackupMissed` | no successful backup for 26 h (not while paused) |
| `BackupJobFailed` | a VolSync mover, retention or maintenance Job failed |
| `PostgresWALArchivingStuck` | > 10 WAL files waiting for 30 min |
| `RestoreTestFailed`, `RestoreTestMissed` | a monthly self-check failed / hasn't passed for 35 days |
| `FluxResourceNotReady` | a Flux Kustomization, HelmRelease or source not Ready for 15 min |
| `CertificateExpiringSoon`, `CertificateNotReady` | < 14 days left / not Ready for 1 h |
| `UPSOnBattery`, `UPSLowBattery`, `UPSExporterDown` | from NUT on host01 (`nut-exporter`) |
| `NASSpaceLow`, `ProxmoxStorageLow` (+ the chart's node/disk/PVC rules) | < 10 % free on the NAS / > 90 % used on a Proxmox storage |
| Backrest (on the NAS) | any backup/check error or warning; missed runs only with the optional healthchecks.io key |
| `restic-maint` (on the NAS) | forget/prune failed |

Schedules and retention are variables in `backups.yml`. Restic and VolSync times are **UTC**
(VolSync's cron), and sources that start in the same hour are staggered by 7 minutes.

**Encryption:**
- **Everything in B2** is encrypted at rest by Backblaze (**SSE-B2**, AES256, set per bucket in OpenTofu).
- **restic** repositories are also encrypted **client-side**, with `RESTIC_PASSWORD` from Infisical.
- **PBS** chunks are encrypted client-side if the PVE storage uses an encryption key (not configured
  today; see the PBS section).
- **barman** traffic goes over TLS.

## Setup (order)

1. **Backblaze account setup** (once, by hand: the only manual secret).
   - Find your account's region (the B2 web UI shows it, e.g. `us-east-005`). Set `b2_region` and
     `b2_s3_endpoint` in `backups.yml`.
   - Choose **globally unique** bucket names in `b2_buckets`.
   - Create ONE application key for OpenTofu, with only the capabilities to manage buckets
     (incl. Object Lock) and keys:
     ```bash
     b2 key create artzima-tofu listBuckets,listAllBucketNames,readBuckets,writeBuckets,readBucketEncryption,writeBucketEncryption,readBucketRetentions,writeBucketRetentions,listKeys,writeKeys,deleteKeys
     ```
     Or use the web UI, *Application Keys → Add a New Application Key*, all buckets, read and write.
     The master key also works, but don't use it.
   - Store it in Infisical as `/tofu/B2_ADMIN_KEY_ID` and `/tofu/B2_ADMIN_APPLICATION_KEY`.
2. `make bootstrap` generates `/k8s/backup/RESTIC_PASSWORD` and `/ansible/NAS_RESTIC_PASSWORD`
   (`make gen-secrets`). **Also keep a copy outside the lab** (emergency kit), e.g. printed.
   Without them, the restic backups can't be read.
3. `make bootstrap` then runs `b2-apply` (alone: `make b2-apply`, plan + `yes`). This creates the
   buckets (Object Lock where configured) and per bucket a backup key and a maintenance key (PBS:
   one), and writes them into Infisical (`/k8s/backup/PG_B2_*`, `RESTIC_B2_*`, their `_MAINT_`
   twins, `/ansible/PBS_B2_*`, `/ansible/NAS_B2_*`). Buckets have `prevent_destroy`.
4. `make render`, commit, push. Flux:
   - installs the Barman Cloud plugin and VolSync (infra-controllers);
   - syncs the `b2-pg` and `*-restic` Secrets;
   - starts archiving WAL and creates the ReplicationSources.

   This must happen **before** the cluster's first Flux sync, or right after `b2-apply`: the
   `secrets` Kustomization waits for every key.
5. `make pbs-offsite` (PBS ≥ 4.2; see [PBS](#pbs-proxmox-guests)). Also
   `make nas-backup` (asks for the NAS sudo password), Backrest on the NAS for the media library and personal shares
   ([NAS media and personal files](#nas-media-and-personal-files)). It doesn't depend on the cluster.
6. **Check** after the first night:
   ```bash
   kubectl get replicationsources -A           # LAST SYNC set, no errors
   kubectl -n vaultwarden get backups.postgresql.cnpg.io   # *-db-b2-* completed
   kubectl -n vaultwarden get cluster vaultwarden-db -o jsonpath='{.status.conditions}' | jq '.[] | select(.type=="ContinuousArchiving")'
   ```
   PBS: *Datastore artzima-b2 → Content* lists the synced groups.

## Postgres (CNPG + Barman Cloud plugin)

- **What runs:** each cluster has `spec.plugins: barman-cloud.cloudnative-pg.io` with
  `isWALArchiver: true` and an `ObjectStore` named `b2` in its namespace.
  - **WAL** is shipped continuously (gzip).
  - A **base backup** is taken nightly (`ScheduledBackup <ns>-db-b2`, `method: plugin`).
  - Retention (`backup_pg_retention`, 30d) is **not** in the ObjectStore: the CronJob
    `<cluster>-retention` applies it weekly with the maintenance key
    ([Immutability](#immutability-what-a-leaked-or-rogue-key-can-do)). B2 then purges the hidden
    files after the lock + `b2_days_hidden_to_deleted`.
- **Credentials:** Secret `b2-pg`, created by the ClusterExternalSecret
  (`k8s/secrets/backups/b2-pg.yaml`) in every namespace labelled `artzima.io/cnpg-offsite: "true"`.
- **A new CNPG cluster:**
  1. Label its namespace.
  2. Copy the `plugins` block, the `ScheduledBackup … -db-b2` and the `ObjectStore b2` from
     `k8s/apps/vaultwarden/database.yaml`, changing the namespace and names. `make render` then
     adds its retention CronJob and monthly restore test (found via `k8s/apps/*/database.yaml`).

### Restore runbook: Postgres point-in-time recovery (PITR)

Example: Paperless, back to 2026-12-01 14:30 UTC.
1. Stop the writer: `flux -n paperless suspend helmrelease paperless && kubectl -n paperless scale deploy/paperless --replicas 0`.
2. In `k8s/apps/paperless/database.yaml`:
   - Rename the cluster to `paperless-db-restore`, or delete the old one first:
     `kubectl -n paperless delete cluster paperless-db`. Its PVC folder stays on the NAS (`Retain`).
   - Replace `bootstrap.initdb` with:
     ```yaml
     bootstrap:
       recovery:
         source: origin
         database: paperless
         owner: paperless
         recoveryTarget:
           targetTime: "2026-12-01 14:30:00+00"   # omit recoveryTarget = latest WAL
     externalClusters:
       - name: origin
         plugin:
           name: barman-cloud.cloudnative-pg.io
           parameters:
             barmanObjectName: b2
             serverName: paperless-db             # the ORIGINAL cluster's name in the bucket
     ```
   - Change the cluster's own `plugins[0].parameters` to write to a **new** `serverName`
     (add `serverName: paperless-db-r1`). This way the restored cluster doesn't overwrite the
     archive you restored from.
3. Commit and push. Wait for `kubectl -n paperless get cluster` to show healthy.
4. If you renamed the cluster, point `PAPERLESS_DBHOST` at `<new-name>-rw`. The app Secret is
   `<new-name>-app`.
5. Start the app: `kubectl -n paperless scale deploy/paperless --replicas 1 && flux -n paperless resume helmrelease paperless`.
6. Later, put `initdb` back in git. A leftover `recovery` block would run again if the cluster
   were ever re-created.

The faster on-NAS alternatives are the CNPG volume snapshot (manual steps §12.4 A, §13.4) and
Vaultwarden's encrypted `pg_dump` (§12.4 B).

## App volumes and NAS folders (VolSync + restic)

- **What runs:** one `ReplicationSource` per entry of `backup_volumes` in `backups.yml`, generated
  by `make render`.
  - **Repository:** one restic repository each, at
    `s3:https://<endpoint>/<restic bucket>/<namespace>/<pvc>`.
  - **Copy method:** `Direct`. The mover mounts the live NFS volume; no snapshot is needed.
  - **Runs as:** the volume's owner (`uid`/`gid` in the list). The `backup` namespace may run
    root movers, for folders of any owner.
  - **Retention:** not in the mover (it only adds). `backup/restic-maintenance` runs `restic forget`
    with the keep values + `--prune`, weekly, with the maintenance key.
- **Adding a volume:** add a line to `backup_volumes`, run `make render`, commit, push.
- **Consistency:** a live copy. Fine for files written atomically (documents, attachments,
  backups). Apps with a database keep it in CNPG, or write their own consistent backup files
  (Sonarr/Radarr/Lidarr/Prowlarr are on CNPG `arr-db`; Bazarr's SQLite has its own
  `/config/backup/*.zip`, restore from those if a live SQLite copy is torn).

### Restore runbook: restic restore of a PVC

**In-cluster (VolSync), e.g. `paperless-media` as of the latest snapshot:**
1. Stop the app (scale to 0, suspend its HelmRelease), as above.
2. Restore into the **existing** PVC:
   ```yaml
   apiVersion: volsync.backube/v1alpha1
   kind: ReplicationDestination
   metadata: { name: paperless-media-restore, namespace: paperless }
   spec:
     trigger: { manual: restore-1 }
     restic:
       repository: paperless-media-restic          # the same Secret the source uses
       destinationPVC: paperless-media
       copyMethod: Direct
       moverSecurityContext: { runAsUser: 1000, runAsGroup: 1000, fsGroup: 1000 }
       # restoreAsOf: "2026-12-01T00:00:00Z"        # optional: latest snapshot before this time
       # previous: 1                                # optional: skip N newer snapshots
   ```
   `kubectl apply -f`, then watch `kubectl -n paperless get replicationdestination paperless-media-restore -w`
   until `latestMoverStatus.result: Successful`.
3. Delete the ReplicationDestination, then start the app.

**Without Kubernetes** (any machine with restic, e.g. after losing the cluster):
```bash
export AWS_ACCESS_KEY_ID=<RESTIC_B2_KEY_ID> AWS_SECRET_ACCESS_KEY=<RESTIC_B2_APPLICATION_KEY>
export RESTIC_PASSWORD='<RESTIC_PASSWORD>'
export RESTIC_REPOSITORY=s3:https://s3.us-east-005.backblazeb2.com/artzima-restic/paperless/paperless-media
restic snapshots
restic restore latest --target /restore/paperless-media      # then copy back to the NAS folder
```
The values are in Infisical (`/k8s/backup`), and the endpoint and bucket are in `backups.yml`.

## PBS (Proxmox guests)

- **What PBS supports:** PBS **4.2** (April 2026) made **S3 datastores** fully supported; they
  were a tech preview in 4.0/4.1.
- **What `make pbs-offsite` sets up:**
  - an S3 endpoint `backblaze`: `{bucket}.s3.<region>.backblazeb2.com`, with the Backblaze quirk
    `skip-if-none-match-header`;
  - an S3-backed datastore `artzima-b2` (`pbs_b2_datastore`) in the **pbs** bucket, with a local
    cache at `pbs_b2_cache_path`;
  - a **local sync job** (pull, no remote) from the local datastore `artzima` to `artzima-b2` at 04:30;
  - a prune job (7/4/6) and a weekly GC on `artzima-b2`.
  - (PBS ids need at least 3 characters, so the first names, `b2`, were refused.)
- **The sync job keeps the bucket's own history:** it uses `--remove-vanished false`, so a mistake
  on the local datastore isn't mirrored into the bucket. Pruning `artzima-b2` is separate.
- **Disk layout:** the PBS OS is on the ZimaBoard's eMMC (~24 GiB root). The external USB disk,
  found by `pbs_datastore_disk_serial`, is the datastore disk only: a GPT with two ext4 partitions, both mounted by UUID in `/etc/fstab` with `nofail`:
  p1 `artzima-pbs`, the rest of the disk, at `/mnt/datastore/<name>` (the local datastore is the
  filesystem root), and p2 `artzima-pbscache` (GPT name `artzima-pbs-cache`; ext4 labels stop at
  16 characters), `pbs_datastore_cache_gib` = 100 GiB at the end of the disk, at
  `/mnt/datastore-cache`: the cache of the B2 datastore (`pbs_b2_cache_path`
  `/mnt/datastore-cache/b2`).
  Formatting is a **one-time opt-in**: `pbs_datastore_format_disk: true` plus
  `pbs_datastore_format_confirm_serial` pinned to that disk's serial (refused on any mismatch);
  afterwards both filesystems are labelled and never formatted again; set the flag back to `false`
  (role `pbs`, `tasks/datastore_disk.yml`; [OPERATOR-SETUP B1](OPERATOR-SETUP.md#b1-install-and-deploy)).
  A disk in the old single-partition layout is re-partitioned only with that opt-in, which **erases
  the local datastore** (it was done on 2026-11-24 and restarted the datastore empty); without it the
  role refuses.
- **Local cache:** PBS wants **64-128 GiB** for it, on its own disk or partition, and it may **not**
  be inside the local datastore. The eMMC root is too small, hence the cache partition above.
  `make pbs-offsite` **refuses** with less than `pbs_offsite_cache_min_free_gib` (64) free, or a path
  inside the datastore.
- **Unverified:**
  - Whether a pull sync job **without** `--remote` copies between two local datastores. The CLI
    allows it; the docs have no worked example. If PBS rejects it, add a remote that points at
    the PBS itself (`proxmox-backup-manager remote create self --host 127.0.0.1 …`) and use it as
    `--remote`.
  - Backblaze may also need `--path-style true` on the endpoint (one forum report).
- **Client-side encryption:** not configured today. The PVE `pbs` storage has no encryption key,
  so chunks in B2 are protected by SSE-B2 only. To add it, set an encryption key on the PVE storage
  (`pvesm set pbs --encryption-key autogen`), keep a copy of it outside the lab (it ends up in
  `/etc/pve/priv/storage/pbs.enc`), and note that only new backups are encrypted.

### Restore runbook: PBS from B2 (the PBS box is lost)

1. Reinstall PBS (≥ 4.2) and run `make pbs`. The local datastore starts empty.
2. Attach the existing datastore instead of creating a new one:
   `make pbs-offsite ANSIBLE_ARGS="-e pbs_offsite_reuse_datastore=true"`. This re-creates endpoint
   `backblaze` and the datastore with `--reuse-datastore true --overwrite-in-use true` under the **same
   name** (`pbs_b2_datastore`), because the name is the object prefix in the bucket.
3. In PVE, add the S3 datastore as a storage: *Datacenter → Storage → Add → Proxmox Backup Server*,
   datastore `artzima-b2`. Or restore straight from the PBS UI.
4. Restore guests from it as usual. Optionally sync `artzima-b2` back to the local datastore (a sync job in
   the other direction).

## NAS media and personal files

**The NAS's personal shares are outside the lab.** They hold the operator's own files, not lab
data, and this repo **never writes** to them. Everything it writes on the NAS is inside
`/volume1/Artzima`, and `make lint` enforces that. The off-site backup below only **reads** them,
through read-only mounts.

The media library (`/volume1/Artzima/data/media`) and the personal shares go to Backblaze B2
according to `backup_nas_media` in `ansible/group_vars/all/backups.yml`:

| Mode | What runs | Notes |
|---|---|---|
| **`restic-on-nas`** (default) | **Backrest** (restic plus a web UI) in Docker **on the NAS** (role `nas_backup`, `make nas-backup`). It writes into a **dedicated** bucket (`b2_bucket_nas`) with its own scoped key (`tofu/backblaze`) and its **own** restic password | independent of the compute hosts; verify backup coverage before retiring an existing provider ([migration](#backup-provider-transition)) |
| `existing` | the old UGOS backup app job (record: `nas_existing_backup` in `backups.yml`) | kept as an option only; the repo creates nothing |
| `off` | nothing | documented as **not** backed up off-site |

`tofu test` asserts that `restic-on-nas` creates exactly one private, single-bucket key and bucket,
and that `existing`/`off` create none.

### Backrest on the NAS

| | |
|---|---|
| Image | `ghcr.io/garethgeorge/backrest:v1.14.1` (`nas_backrest_tag`) |
| Files on the NAS | `/volume1/Artzima/backrest/{compose.yaml, config/, data/, cache/, tmp/, restore/}`, root-owned, mode 0700. The config holds secrets |
| Sources (read-only bind mounts) | `/volume1/Artzima/data/media` → `/userdata/media`; each `nas_personal_shares` entry → `/userdata/<name>` |
| Repository | restic at `s3:https://<b2_s3_endpoint>/<b2_bucket_nas>/restic`, key `/ansible/NAS_B2_*`, password `/ansible/NAS_RESTIC_PASSWORD` |
| Plans | `media-daily` (`0 1 * * *`); `media-weekly-full` (`0 3 * * 0`, `--force`: re-reads every file); `personal-daily` (`30 0 * * *`, all listed shares) |
| Retention | Backrest keeps all (its key only adds). The **`backrest-maint`** container (`restic/restic:0.20.0` + crond, same compose project, files in `backrest/maint/`) runs `restic forget` 7 daily, 4 weekly, 12 monthly (`nas_backup_keep_*`) `--prune` Saturdays 06:00 UTC with the **maintenance** key |
| Check | monthly `restic check --read-data-subset=5%` (1st, 05:00; `nas_backup_check_*`) |
| Bandwidth | `--limit-upload=<nas_backup_upload_limit_kib>` KiB/s on every restic call (default 2500 KiB/s ≈ 20 Mbit/s; 0 = unlimited). restic runs with low CPU and IO priority |
| Schedule window | Start times are the cron values above. An optional **hard stop** at `nas_backup_window_stop_hour` restarts the container from root's crontab on the NAS, which stops a still-running backup; restic reuses what was already uploaded on the next run, and `autoUnlock` clears the stale lock. UGOS updates may reset the crontab, so re-run `make nas-backup` after one |
| Web UI | `http://192.0.2.156:9898`: published on the NAS **lab-LAN address only**, so reachable from the lab LAN and, from the home network or anywhere else, over the Tailscale subnet routers; never port-forwarded. Login from Infisical (below) |

**restic is always incremental:** each run uploads only new or changed data. "Weekly" (`--force`)
re-reads every file to catch content changes that size/mtime don't reveal. That costs disk reads,
not uploads.

**The repo owns the config.** Ansible renders it and applies it only when the repo's rendering
changes. Backrest's own additions (the repo `guid` after auto-init, `modno`) stay in the live file,
but plans or repos edited in the UI are overwritten by the next `make nas-backup`.

#### Setup (once)

1. **Infisical:** `make bootstrap` generated everything: `/ansible/NAS_RESTIC_PASSWORD` (**keep a
   copy outside the lab**: without it nothing can be restored), `NAS_BACKREST_USER` (`admin`),
   `NAS_BACKREST_PASSWORD_BCRYPT` (base64(bcrypt) of `/operator/BACKREST_PASSWORD`, your UI login),
   `NAS_BACKUP_HEALTHCHECKS_URL` (empty), and the alert URL `/k8s/alerts/WEBHOOK_URL` (empty).
2. **Bucket and keys:** `make b2-apply` (part of `make bootstrap`) creates `b2_bucket_nas` and
   writes `/ansible/NAS_B2_*` (backup) and `/ansible/NAS_B2_MAINT_*` (maintenance).
3. **Shares:** after inspecting the NAS (`ls -la /volume1`), list the personal shares in
   `nas_personal_shares` (`{ name: photos, path: /volume1/Photos }`; quote paths with spaces or `'`,
   no `:`). `nas_backup_excludes` (default `#recycle`, UGOS's per-share recycle bin) applies to every plan. A share inside `/volume1/Artzima`
   is refused.
4. **UGOS prerequisites:**
   - the **Docker** app is installed (`docker0` exists, so it is);
   - SSH is enabled for `devartech`, which must be an **administrator** (UGOS admins have `sudo`);
   - `docker compose version` works (UGOS' Docker app ships the compose plugin);
   - for Ansible, `python3` exists on the NAS (`ssh devartech@192.0.2.156 python3 --version`).

   Ansible runs everything with `sudo`, so `devartech` doesn't need to be in the `docker` group.
5. **Deploy:** `make nas-backup` (part of `make up`; it lists the tasks, asks `yes`, then the sudo
   password: `NAS_ANSIBLE_ARGS=` if sudo needs none). It renders `compose.yaml`, the config and the
   `maint/` files, then runs `docker compose up -d`. Re-run it after any change in `backups.yml`
   or Infisical.

   **If Ansible can't manage UGOS** (no `python3`, a different Docker layout), use the one-time
   manual install:
   ```bash
   make nas-backup NAS_ANSIBLE_ARGS= ANSIBLE_ARGS="-e nas_backup_deploy=false"   # renders into ansible/out/nas-backup/ (gitignored, has secrets)
   scp -r ansible/out/nas-backup/compose.yaml ansible/out/nas-backup/config ansible/out/nas-backup/maint devartech@192.0.2.156:/tmp/backrest-new/
   ssh -t devartech@192.0.2.156 'sudo mkdir -p /volume1/Artzima/backrest/{config,data,cache,tmp,restore,maint} \
     && sudo install -m 600 /tmp/backrest-new/compose.yaml /volume1/Artzima/backrest/compose.yaml \
     && sudo install -m 600 /tmp/backrest-new/config/config.json /volume1/Artzima/backrest/config/config.json \
     && sudo install -m 600 /tmp/backrest-new/maint/maint.env /volume1/Artzima/backrest/maint/maint.env \
     && sudo install -m 644 /tmp/backrest-new/maint/crontab /volume1/Artzima/backrest/maint/crontab \
     && sudo install -m 755 /tmp/backrest-new/maint/maint.sh /volume1/Artzima/backrest/maint/maint.sh \
     && sudo chmod 700 /volume1/Artzima/backrest /volume1/Artzima/backrest/* \
     && rm -rf /tmp/backrest-new \
     && sudo docker compose -f /volume1/Artzima/backrest/compose.yaml up -d'
   rm -rf ansible/out/nas-backup
   ```
   Alternatively, UGOS' Docker app → *Project* → *Create* → path `/volume1/Artzima/backrest` imports
   the same `compose.yaml`.
6. **First run:** open the web UI, check that repo `b2-nas` initialized (it is created
   automatically), then start `personal-daily` and `media-daily` by hand (*Backup now*), or wait
   for the schedule. The first full upload takes days ([estimate](#backup-provider-transition)).

#### Alerts: failures and missed runs

- **Failures and errors:** every backup error or warning and every check failure, from any plan,
  is sent to THE alert URL (`/k8s/alerts/WEBHOOK_URL`, shared with Alertmanager). The role hands it
  to Backrest as a **Shoutrrr** generic webhook (`generic+https://…`; Backrest 1.14 has no working
  plain webhook action). The `backrest-maint` container posts a small JSON to the same URL when
  forget/prune fails. Empty = no alerts. After changing the URL, re-run `make nas-backup`.
- **Missed runs:** a backup that never starts sends no error, so only a **dead-man's switch** catches
  it. The free [healthchecks.io](https://healthchecks.io) does this.
  1. Create a project and copy its **ping key**.
  2. Store `https://hc-ping.com/<ping-key>` as `NAS_BACKUP_HEALTHCHECKS_URL`.
  3. Each plan then pings its own check, `artzima-nas-<plan>` (start, success, fail), and the checks
     are auto-created on the first ping (`?create=1`).
  4. In healthchecks.io, set each check's **period and grace**: `media-daily` and `personal-daily`
     1 day with 2 h grace (more during the first upload); `media-weekly-full` 7 days with 1 day grace.
  5. Add its e-mail/Signal/… integration, or later Headquarters.

#### Restore runbook: NAS files from Backrest/restic

- **A few files (web UI):** *Plan* → *Snapshots* → pick one → *Restore*.
  - Target: a folder under **`/restore`**, which is `/volume1/Artzima/backrest/restore` on the NAS
    and the only writable mount.
  - Then copy the files back by hand (UGOS file manager or `cp -a`); the sources are mounted
    read-only on purpose.
- **Without Backrest or the NAS** (any machine with restic):
  ```bash
  export AWS_ACCESS_KEY_ID=<NAS_B2_KEY_ID> AWS_SECRET_ACCESS_KEY=<NAS_B2_APPLICATION_KEY> RESTIC_PASSWORD='<NAS_RESTIC_PASSWORD>'
  export RESTIC_REPOSITORY=s3:https://s3.us-east-005.backblazeb2.com/artzima-nas/restic
  restic snapshots --tag plan:personal-daily        # Backrest tags snapshots with plan:<id>
  restic restore latest --tag plan:personal-daily --include /userdata/photos/2025 --target /restore-here
  ```
  Paths inside snapshots are the container paths (`/userdata/media`, `/userdata/<share>`).

#### Check the last successful run (monthly, and in the quarterly test)

1. **Web UI:** each plan's newest operation is a successful *backup*, newer than its schedule;
   the repo's last *check* (monthly) passed.
2. **healthchecks.io:** all `artzima-nas-*` checks are green.
3. **B2:** *Buckets → `artzima-nas`*. The size grows roughly with the library, and the newest files
   are from the last run.
4. **Spot restore:** restore one recent rip and one personal file into `/restore`, and compare
   `sha256sum` with the originals.

### Backup-provider transition

The order is fixed. Keep the existing backup until the new one is **verified**:

1. **Deploy Backrest** (above) while the existing backup provider still runs.
2. **Upload to completion.** Watch the web UI until `media-daily` and `personal-daily` have each finished one
   full snapshot. Expect days, and plan around the uplink:

   | Uplink actually available for backup | Time per TB (≈ 8×10¹² bits) |
   |---|---|
   | 10 Mbit/s | ~9.3 days |
   | 20 Mbit/s (≈ the default limit, 2500 KiB/s) | ~4.6 days |
   | 50 Mbit/s | ~1.9 days |
   | 100 Mbit/s | ~22 hours |
   | 250 Mbit/s | ~9 hours |

   Formula: `hours ≈ TB × 8,000,000 / Mbit/s / 3600`, plus about 10-20 % protocol overhead.
   Deduplication and compression only help a little with already-compressed video.
   Measure the uplink first (e.g. a speed test while nothing else runs). If you lower
   `nas_backup_upload_limit_kib`, re-run `make nas-backup`. Optionally set `nas_backup_window_stop_hour`.
3. **Verify the new backup:**
   - In the web UI, *Repo `b2-nas` → Run check*. For the first verification, `--read-data-subset`
     of 10-20 % is better (run it from the CLI above if you want more than the scheduled 5 %).
   - Restore a few files from each plan (a large and a small rip, several personal files from
     different shares, and the oldest file you have) into `/restore`, and compare `sha256sum`
     with the originals.
   - Confirm that the healthchecks.io checks are green and that a deliberately broken run alerts.
     For example, pause the bucket key in B2 for one manual run, then restore it.
   - A share that is still **empty** (allowed: it is backed up from day one) has nothing to restore;
     check that its folder appears in the latest `personal-daily` snapshot.
4. **Only then, MANUALLY (never automated by this repo).** What the previous backup is (the tool,
   container name, config folder, bucket) is recorded in `nas_existing_backup`; the private
   [NAS plan](nas-plan.md) shows it.
   - **Stop it.** If it is a Docker container on the NAS:
     `sudo docker update --restart=no <container> && sudo docker stop <container>`. If it is a UGOS
     app, disable its job there. Keep its **config folder**: it holds the job definition and the
     passphrase you would need to read the old backup.
   - After another week or two of green Backrest runs: **remove** the container
     (`sudo docker rm <container>`), then **delete its B2 data** in the B2 web UI (its bucket or
     prefix, and any key made only for it), according to the retention policy. Delete the old
     config folder last.
   - Update `nas_existing_backup`'s notes (retired, date). `backup_nas_media` stays `restic-on-nas`.
5. **Temporary double cost:** while both copies exist, B2 bills both, at about
   `(size of the media + shares in TB) × $6.95` per month **extra**, for the weeks of the
   migration. A 4 TB library costs about $28/month more until the previous backup copy is retired.
   Remember that B2 keeps hidden files until the lifecycle purges them. The old bucket has its
   own rules; delete the bucket itself to stop billing for it.

## Cost estimate inputs (B2, checked 2026-11-23)

- **Storage:** **$6.95 per TB-month**; the first 10 GB is free. B2 has no minimum file size and
  no minimum storage duration.
- **Egress:** free up to 3× your average stored data per month, then $0.01/GB. A full restore is
  normally free.
- **API calls:** class A/B/C are free; class D is $0.004 per 10k, with 2,500/day free.
- **Hidden versions:** deleted versions count until the lifecycle rule purges them
  (`b2_days_hidden_to_deleted`, 7 days).

Estimate = (Postgres base backups × retention + WAL) + restic repos (deduplicated; roughly the live
data plus about 10-20 % for history) + PBS (deduplicated chunks of all guests). Read the real numbers
monthly in the B2 web UI, under *Buckets* (size per bucket).

## Quarterly restore test (checklist)

**Twice a year (e.g. January and July), instead of the quarterly test:** the **full-restore drill** from
[disaster recovery: Drills](disaster-recovery.md#drills). It uses the printed emergency kit and a
clean computer only (`scripts/dr-tools.sh` installs the tools): restore a sample from every bucket,
and walk the rebuild to "Flux Ready" on a throw-away cluster. Also run
`make emergency-kit EK_ARGS=--infisical`, refresh any stale kit item, and reprint with `make dr-pdf`. The quarterly items below apply in the other two quarters.


Do this every quarter, and after any change to the backup code. Write the date and the results
in the TODO list of the README.

- [ ] **B2:** all three buckets are growing as expected, there are no failed lifecycle or key
      errors, and *Caps & Alerts* are set.
- [ ] **Postgres PITR:**
  - restore `vaultwarden-db` into a **new** cluster `vaultwarden-db-test` with a `targetTime`
    of yesterday noon, and a new `serverName`;
  - `kubectl cnpg psql`, or a pod with `psql`, then `select count(*) from users;`;
  - delete the test cluster afterwards.
- [ ] **restic:**
  - `ReplicationDestination` restore of `alexandria-library` into a **new** test PVC;
  - mount it in a busybox pod and spot-check files;
  - delete the PVC and its folder.
- [ ] **restic without Kubernetes:** from the workstation, `restic snapshots` and
      `restic check --read-data-subset=1/20` on one repository.
- [ ] **PBS:**
  - restore a small LXC (e.g. a ts-router) from datastore **`artzima-b2`** to a spare VMID;
  - boot it with no network;
  - delete it.
- [ ] **NAS media + personal files (Backrest):**
  - last successful run of every plan, and the monthly check, in the web UI;
  - healthchecks.io all green;
  - one rip and one personal file spot-restored and checksummed

- [ ] **Paperless:** in `/volume1/Artzima/backups/paperless`, open `manifest.json`, pick a document
